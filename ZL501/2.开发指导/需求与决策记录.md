## 2. 文档体系与优先级

1. 《嵌入式编程规则手册》是代码合规、工具链、格式、接口契约和验证要求的上位规范。
2. 《嵌入式程序开发指导书》是开发实施文件，重点规定开发流程、函数分级、资料库、人工审核、模板及示例的使用方法。
3. 两份文件不得形成相互冲突的要求。内容重叠时，指导书引用对应 EPR 规则编号，不大段复制规则正文。
4. 本记录中的用户偏好与 EPR 强制规则冲突时，以 EPR 为准，并在本记录中保存原始意图和调整后的执行口径。
5. 后续程序开发必须同时遵守《嵌入式编程规则手册》和已批准的《嵌入式程序开发指导书》。

### 2.1 指导书标识

《嵌入式程序开发指导书》采用独立文档标识：

```text
EDI — Embedded Development Instruction
```

EDI 与 EPR 的职责严格区分：

- EPR 规定代码必须满足的编程规则和合规判据；
- EDI 规定如何组织、实施、审核和交付嵌入式程序开发活动；
- EDI 引用 EPR 的稳定规则编号，不复制 EPR 的完整规则正文；
- EDI 不得修改、降低或替代 EPR 的强制要求。

### 2.2 指导书版本与状态

EDI 采用 `主版本.次版本.修订版本`：

- 主版本：存在不兼容的开发流程、模板、资料库结构或审核要求变化；
- 次版本：兼容增加流程、模板、检查项或章节；
- 修订版本：不改变执行要求的文字、链接、示例或排版修正。

编制期间使用 `0.1.0-draft`；全部章节、模板、示例和最终审查完成并经人工批准后，首次正式发布为 `1.0.0`。文档状态采用：

```text
草案 / 评审中 / 正式发布 / 已废止
```

EDI 必须独立维护版本变更记录，并记录每个版本所依据及适配的 EPR 版本。EPR 基线变化后，EDI 必须重新核对，兼容性明确记录为 `兼容`、`需要修改` 或 `无法判断`，不得默认继续兼容。

版本记录至少包含：

| 字段 | 含义 |
| --- | --- |
| EDI 版本 | 本次指导书版本 |
| 日期 | 版本形成或发布日期 |
| 变更类型 | initial、major、minor 或 patch |
| 涉及 EDI 编号 | 受影响的稳定要求编号 |
| 变更说明 | 实际改变内容 |
| 适配 EPR 版本 | 本版核对的上位规范基线 |
| EPR 兼容性 | 兼容、需要修改或无法判断 |
| 批准状态 | 草案、待批准或已批准 |

EDI 不建立独立的 `.clang-format`、`.editorconfig` 或同类格式工具基线；相关配置继续由 EPR 管理。

### 2.3 章节编号与稳定要求编号

EDI 同时采用两类编号：

1. 使用 `1`、`1.1`、`1.1.1` 形式组织章节层级；
2. 仅为可执行、需审核或需追踪的要求分配稳定编号。

普通说明、理由、背景和示例不单独分配稳定编号，避免把 EDI 扩展为重复的第二份编程规则。

稳定编号采用 `EDI-类别-三位序号`：

| 编号前缀 | 适用内容 |
| --- | --- |
| `EDI-GOV` | 文档治理、版本、适用范围和优先级 |
| `EDI-STD` | C 标准、工具链和项目配置确认流程 |
| `EDI-ARC` | 模块划分和开发结构 |
| `EDI-CLS` | Service、Composite、Atomic 函数分类 |
| `EDI-DEV` | 程序开发步骤和函数实现流程 |
| `EDI-DOC` | `.c/.h/.md` 资料库及注释维护 |
| `EDI-REV` | 人工审核、AI 审核和变更检查 |
| `EDI-TPL` | 模板使用和实例化要求 |
| `EDI-REL` | 完成判定、交付和发布流程 |

编号一经正式发布不得回收或改变原义。要求废止时保留编号并标记状态；发生实质含义变化时评估新编号和版本影响。

### 2.4 EDI 要求条目的精简结构

EDI 不完整复制 EPR 每条规则的重型结构。具有稳定编号的 EDI 要求原则上使用：

```markdown
#### EDI-CLS-001 要求标题

- 执行等级：必须 / 应 / 可以
- 执行阶段：适用开发阶段
- 审核方式：AI 初审 / 人工批准 / 工具辅助
- 关联规则：对应 EPR 编号或“不适用”

要求：
明确、可执行的实施要求。

完成证据：
用于人工复核的最小必要证据。
```

不得在 EDI 中通过重新表述改变 EPR 约束等级。EDI 的完成证据用于证明开发步骤已执行，不代替 EPR 所要求的编译、测试、目标验证或偏离审批证据。

## 5. 函数三级分类

### 5.1 分类名称与定义

| 分类 | 定义 | 允许的项目内调用关系 | 默认可见性 |
| --- | --- | --- | --- |
| Service Function | 向调用方提供完整服务、控制能力或模块级业务接口 | 可调用 Service、Composite 和 Atomic | 按实际调用方需要公开 |
| Composite Function | 完成模块内部较复杂的子流程 | 可调用 Composite 和 Atomic；不得形成递归 | `static` 私有 |
| Atomic Function | 只完成一个简单、单一的操作 | 不调用项目内 Service、Composite 或 Atomic；允许调用标准库、HAL、RTOS API 和宏 | `static` 私有 |

### 5.2 分类约束

- 禁止直接递归和间接递归。
- 不另设函数行数或圈复杂度的强制阈值；仍必须遵守 EPR-API-001 的单一职责要求。
- EPR-API-002 的 50 行是建议性审查信号，不是强制上限，指导书不得将其删除、降级或改写为不存在。
- Service 并不自动等同于公共接口；只有调用方确实需要的接口才能公开。
- Composite 和 Atomic 默认使用 `static` 限制链接范围。确需跨翻译单元使用时，必须重新审查其职责和接口归属，并遵守 EPR-MOD-003 与 EPR-MOD-011。
- 每个函数的分类必须经过人工审核。AI 初次分类在资料库中标记为 `Pending Review`，人工确认后标记为 `Approved`。

### 5.3 `@brief` 分类句式

分类信息放在 `@brief` 的开头，使用以下固定英文句式：

```text
This is a Service Function.
This is a Composite Function.
This is an Atomic Function.
```

固定句式之后继续说明函数的真实职责，不能只写分类而省略功能描述。

## 6. 函数文档决策与上位规则校正

### 6.1 用户期望

函数前置文档原计划仅使用 `@brief`、`@param`、`@return`、`@author` 四种命令；参数方向、输入和输出信息原计划只写入对应 Markdown 资料库；`@author` 默认填写 `Nan.Wang`。

### 6.2 核对结果

上述计划不能原样作为公共接口规则执行，原因如下：

| 原计划 | 上位规则 | 判定与最终口径 |
| --- | --- | --- |
| `@param` 不写方向，方向只放资料库 | EPR-DOC-005 强制每个显式形参使用 `[in]`、`[out]` 或 `[in,out]` | 存在直接冲突。源码公共接口必须写方向；资料库同时记录方向，不能取代源码契约 |
| 文档命令仅限四种 | EPR-DOC-004、EPR-DOC-006、EPR-DOC-007 要求按适用性使用 `@retval`、`@pre`、`@post`、`@note`、`@warning` 等字段 | 存在直接冲突。公共接口必须包含 EPR 要求的适用字段；不得以四字段限制删除强制契约 |
| 删除可重入性、线程安全性、时间约束等信息 | EPR-API-011 和 EPR-DOC-007 强制公共接口公开执行上下文、同步和阻塞/时间属性 | 存在直接冲突。模块资料库可以保持精简，但公共接口权威契约不得删除这些信息 |
| 每个 `.c` 函数定义前重复完整函数文档 | EPR-DOC-004 要求公共函数权威契约位于公共声明之前，实现处只补充实现理由或引用 | 部分冲突。公共函数不在 `.c` 中重复维护完整契约；私有函数在定义前写结构化文档 |
| 所有函数写 `@author Nan.Wang` | EPR-DOC-003 默认以版本控制保存作者与历史，且禁止不准确或复制的作者信息 | 有条件采用。默认作者配置为 `Nan.Wang`，生成时必须确认真实作者；版本控制仍是作者和修改历史的权威机制 |

### 6.3 最终执行口径

- 公共函数：在 `.h` 声明前提供符合 EPR-DOC-004 至 EPR-DOC-007 的英文 Doxygen 契约；实现处不复制契约，只在需要时补充实现理由或稳定引用。
- 私有函数：在 `.c` 定义前提供英文 Doxygen 文档，至少包含 `@brief`、适用的 `@param`、`@return` 和经确认的 `@author`；如其他 EPR 强制契约适用，必须补充对应信息。
- 无参数函数不写虚构的 `@param None`，遵守 EPR-DOC-004。
- `void` 函数必须明确说明无返回值及适用的错误通道或失败前提，遵守 EPR-DOC-004 和 EPR-DOC-006。
- `@author` 默认值为 `Nan.Wang`，模板保留统一配置位置；实际使用前须人工确认其真实性。

## 7. 函数内部逻辑分区

函数按实际存在的逻辑阶段，从下列英文分区中选择：

```c
/* Local Variables */

/* Input Validation */

/* External Data Acquisition */

/* Main Processing */

/* Output Assignment */

/* Debug and Diagnostics */

/* Cleanup and Return */
```

- 不存在相应代码时省略该分区，不生成空分区。
- 短小且逻辑显然的函数不为满足形式而机械分区。
- 分区不得改变声明作用域、初始化时机、资源生命周期、控制流或清理顺序。
- 局部变量仍须按照 EPR-OBJ 及适用语言方言要求声明和初始化。

## 8. 注释原则

- 不以注释行数占源码行数的简单比例衡量质量。
- “90%以上注释率”解释为：需要说明的代码元素和非显然约束，其有效注释覆盖率应达到 90% 以上。
- 函数接口、文件作用、全局及文件作用域对象、公共类型、宏、枚举和非显然算法等必须按 EPR 的适用条款记录。
- 注释重点解释职责、原因、边界、硬件限制和非显然设计，不逐行翻译代码。
- 注释不得损害代码阅读，不得用注释替代实现、验证或安全证据。
- 注释和资料库必须随代码变更同步核验，遵守 EPR-DOC-008 至 EPR-DOC-010。

## 9. 模块资料库

### 9.1 文件对应关系

每一对模块 `.c/.h` 文件对应一个同名 Markdown 文件，例如：

```text
motor_control.c
motor_control.h
motor_control.md
```

Markdown 资料库由 AI 初稿、人工审核和维护；源码及其公共接口契约是实现事实来源，资料库不得覆盖或改写源码真实行为。

### 9.2 精简内容范围

每个模块资料库保留以下关键信息：

- 模块用途及 `.c/.h` 职责边界；
- 函数清单、三级分类及人工审核状态；
- 全局变量和文件作用域变量清单及含义；
- 每个函数的局部变量及含义；
- 参数的 Input、Output 或 Input/Output 方向及含义；
- 函数返回值及含义；
- 必要依赖和使用注意事项。

资料库不单独设置以下专章：

- 可重入性与线程安全性；
- 时间复杂度与最坏执行时间；
- 错误码；
- 单元测试与验证记录。

上述删减只针对模块资料库版式，不能删除 EPR 要求在公共接口、项目配置或验证证据中记录的信息。
